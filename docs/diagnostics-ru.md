# Диагностика внутренней ошибки Void

Диагностика включена в RROP.
Обычная сборка через `examples/build_rings_of_power.py` включает диагностику
автоматически вместе с поддержкой сохранений. После обновления исходников
нужно пересобрать executable; старый бинарь диагностику не содержит.

В оригинальном ROM сообщение «Void has found your party…» используется как
общий экран внутренней ошибки. Число перед словом `seconds` — переданный
код ошибки, а не измеренное время до смерти. Среди подтверждённых причин:

| Код | Причина |
| --- | --- |
| 22 / `0x16` | Нет свободной записи в таблице размещения из 56 записей |
| 26 / `0x1a` | Нет свободной записи в таблице акторов из 56 записей |
| 24 / `0x18` | Объект не найден в кэше размещения |

Это подтверждает существование ограничений, но ещё не устанавливает причину
сбоя после длительной игры. Для этого нужно поймать конкретную ошибку.

## Что записывается

Диагностика хранит в памяти последние 256 изменений первых слов записей обеих
таблиц, адрес инструкции, номер кадра и шаг исполнения. Также учитывает
выделения, освобождения и максимальную заполненность. Занятость определяется
по оригинальным признакам: младшая тетрада слова актора ненулевая; первое
слово записи размещения не равно 9999. История начинается после входа в игру
и сбрасывается при загрузке снимка. Объекты, уже существовавшие на старте
наблюдения, имеют неизвестный адрес создания (`created_pc=000000`).

Перед входом в оригинальный обработчик ошибки `$012FA0` создаются:

- `diagnostics/void-error.txt`: код ошибки, адрес возврата, регистры, обе
  таблицы целиком и история изменений;
- `diagnostics/void-error.grs`: полный снимок машины до отрисовки ошибки.

Файлы находятся внутри каталога сохранений. В Linux по умолчанию это
`${XDG_STATE_HOME}/genesisrecomp/rings-of-power`, либо
`~/.local/state/genesisrecomp/rings-of-power`. В Windows —
`%LOCALAPPDATA%/GenesisRecomp/rings-of-power`. Параметр `--save-dir` позволяет
выбрать другой каталог. В терминал выводится точный путь к отчёту.

Последующая ошибка заменяет предыдущую пару диагностических файлов.
Обычные ручные сохранения и автосохранения не перезаписываются.
Если запись снимка невозможна, отчёт указывает `snapshot=FAILED`.

## Ограничения и дальнейшее исправление

Диагностика не очищает таблицы, не добавляет игровую память и не подавляет
экран ошибки. Аварийный снимок нужен для расследования: загрузка его снова
приведёт к той же ошибке. Он не является исправленным сохранением.

Наши сохранения восстанавливают RAM целиком. Оригинальная загрузка из EEPROM
вызывает `$020CF6` и `$023A9E`, очищающие временные таблицы, и затем
восстанавливает состояние игры. Поэтому наша загрузка не повторяет этот
эффект очистки.

После получения отчёта нужно установить, какие записи накопились и почему
они не освобождаются. Без этого очистка «старых» объектов может удалить
нужного персонажа или предмет. Код на этой стадии проверен чтением;
сборка и игровые тесты не запускались.
